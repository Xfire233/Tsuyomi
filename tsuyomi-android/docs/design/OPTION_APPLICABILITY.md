# 设置项与功能项适用性规则

## 目标

界面只展示当前状态下真实、可解释、可完成的能力。持久化字段的存在不等于该控件在每个上下文都应出现；没有实际效果的控件会制造错误心智模型。

## 判定顺序

每个设置项、动作和入口在设计评审时必须回答：

1. **已实现**：是否存在真实 handler、状态、错误恢复和验证证据；未实现则隐藏，不显示占位入口。
2. **具备能力**：当前设备、API、来源、权限和有效 profile 是否支持该能力。
3. **当前生效**：操作是否会改变当前用户可观察行为，而不是只写入暂时无消费者的值。
4. **需要解释**：即使当前不可操作，用户是否必须看见一个已保留值、阻塞原因或可执行前置条件。
5. **反馈完整**：结果是否以持久、可访问、非动画依赖的方式呈现。

## 可见性矩阵

| 状态 | 呈现 | 约束 |
|---|---|---|
| 当前可用且生效 | 可见、可操作 | 文案描述实际效果；handler 和失败恢复必须存在 |
| 当前不生效，但保存值会在明确的另一上下文恢复 | 可见、禁用 | 显示保存值和恢复条件；不得清除偏好；不得允许无效写入 |
| 缺少用户可解决的前置条件 | 可见、禁用或替换为前置操作 | 必须明确原因和唯一可执行路径 |
| 当前上下文无意义，显示会暗示不存在的能力 | 隐藏 | 值可在后台保留；切回适用上下文时恢复 |
| 未实现、无 handler、结果不可验证 | 隐藏 | 禁止“即将推出”、空响应或假入口 |

禁用不是隐藏的廉价替代。只有“保留值需要被理解”或“用户能解除阻塞”时才使用禁用态。

## DisplayProfile 应用

- profile 选择始终可见，因为它决定上下文本身。
- 深色和动态颜色偏好在 E-ink 下保留并禁用，原因是用户需要知道值未丢失，返回 standard 后会恢复。
- E-ink “立即重绘界面”只在 `effectiveProfile == EINK` 时出现；standard 下隐藏。
- 逻辑刷新策略在存在真实调度消费者和可观察差异前不进入持久模型或 UI；枚举和文档承诺不构成已实现能力。
- 自动识别出的 E-ink 与手动 E-ink 使用相同可见性；判定依据是 effective profile，不是 persisted preference 或设备型号。
- profile 切换只即时增删整个设置 section，不创建第二套 screen tree，不使用 `AnimatedVisibility`，不清空路由、焦点之外的持久状态或偏好。

## 模块边界

- `core/display` 决定 persisted/effective/capability 状态。
- `feature/*` 根据 effective capability 组织 section 和业务文案。
- `core/ui` 提供语义组件，不决定业务能力是否存在。
- `app` 只组合依赖和根环境，不复制 feature 的可见性判断。

同一能力的生效判定必须只有一个源头。Screen 不得根据 `Build.MODEL`、API 字符串或持久枚举自行推导能力。

## 设计与验证要求

每个条件项至少覆盖：

- 可用上下文中存在且可操作；
- 不适用上下文中不存在，或符合矩阵的禁用解释；
- 切换上下文后保存值恢复；
- API 下界、标准/E-ink、自动/手动 profile；
- TalkBack、键盘/DPAD、`fontScale = 2.0`、横竖屏无不可达残留焦点；
- 文案不夸大 Android 通用 API、厂商硬件或未实现能力。

设计评审必须逐项记录“为什么可见、何时生效、无效时为何隐藏或禁用”。缺少答案即阻塞实现准入。
